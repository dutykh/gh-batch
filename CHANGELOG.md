# Changelog

The versions follow semantic versioning: a change that breaks a command line, a setting or the format of `--porcelain` raises the first number.

## 1.6.0, 24 November 2026

Repositories can be named, from any folder. A word of the command line that is not a folder where it was typed is a name, looked up under the folders of `gh-batch.root`: the name that the report shows (`teaching/exam-2026`), its last part (`exam-2026`), or a folder of the root that holds several repositories (`teaching`), with the wildcards of `--only` if wanted. So `gh-batch commit push obsidian notes` works from every folder, where it worked only from the one that held both. A name that matches nothing stops the run before anything is done, and the message lists the names that contain the word. A folder where the command is typed wins over a name, a path is always a folder, and `doctor` looks around the folders named as folders only, not around the root where a name was found.

Several commands can share one line, in the order typed, on the same repositories: `gh-batch pull commit push thesis` brings the thesis up to date, commits under the message asked for, and pushes. Each command prints its own report and asks its own question; a commit followed by a push is the form `commit push`, and a pull followed by a push is `sync`. On such a line `clone` reads the account and its organisations, and the folders and names go to the other commands. A question answered no, an interrupt, or a command that cannot start ends the line, and a repository that needs you in one command does not stop the next. Each command comes once; `-u` is written in full there, and `--manifest` belongs to clone or to list alone.

Every word that names a command is now a command, as `push` after `commit` already was, and the words after `--` are folders or names, never commands. A folder or a repository called like a command, such as `status` or `log`, is therefore given as a path or after `--`, and `gh-batch commit -- push` commits a repository named push instead of pushing. When such a word is also a folder where the line is typed, which it used to name, the run stops before anything is done rather than guess which was meant.

The completion of bash and zsh offers the names of the repositories, by their whole name and by their last part, and the other commands of a line, with the options of every command on it.

## 1.5.0, 17 November 2026

A file that git does not track here, untracked or ignored, no longer stops an update when the new commits of the server put a file in its place. It makes way for the version of the server: it is moved, whole, into the git folder of the repository, `.git/gh-batch/kept/DATE-TIME/`, where nothing can be committed, and the report names it with the command that compares the two versions and the one that takes it back; a copy identical to the version of the server is simply dropped, and a line "Kept aside" at the end of the report lists what was kept. This holds for `pull`, `push`, `sync`, `clone --update` and `reset`. Until now a fast-forward stopped there, with a message that spoke of changes where `git status` showed none, and a `git pull` typed by hand then replaced the ignored file without asking. A merge, with `gh-batch.diverged merge`, replaced an ignored file in the way without a word, as git does; it no longer can.

The new setting `gh-batch.conflicts`, with the option `--conflicts` and the variable `GH_BATCH_CONFLICTS`, decides what follows a conflict. With `report`, the default, the attempt is undone as before. With `server`, the commit of the branch is kept under `refs/gh-batch/before-pull/BRANCH/DATE-TIME`, the version of this machine of each file that both sides changed is copied into the kept folder, and the replay or the merge is made again with the version of the server in the lines that both sides changed. A file that git cannot merge line by line, such as a PDF rebuilt on two machines, takes the version of the server whole, and a commit of this machine left empty by it is dropped and counted in the report, which also prints the one command that restores the branch. A conflict that this cannot settle, a file deleted on one side and changed on the other, is undone as before.

Uncommitted changes travel over an update. When the new commits touch files changed here and not committed, the changes go into a stash of the tool's own, the update is made, and they come back, provided git tells beforehand that they still apply, which needs git 2.40 or newer; a staged change that cannot stay staged comes back unstaged, and the report says so. A replay is no longer refused because of uncommitted changes. When they touch the same lines as the new commits, the repository is blocked as before, or, with `gh-batch.conflicts server`, the version of the server goes in and the changes wait in the stash, the repository being named among those that need you, with the command that brings them back. A stash of yours is never applied or dropped, and changes that a stash would lose (a file added with `--intent-to-add`, a file that git no longer tracks but that stays on the disk, a submodule) keep the old answer.

When the server rewrote its history and every commit here that it lacks was once on it, `pull` takes the new history by itself, with `gh-batch.diverged` set to `rebase` or `merge`: the commit of the branch is kept under a reference first, and the old commits are listed. The other local branches that follow the branch of the same name on the server and only lack its new commits move forward with the branch that is checked out, without a file being touched; a branch checked out in another worktree, or one that follows a branch of another name, as a bookmark made from `main` does, stays where it is.

A fork is compared with the repository it was forked from: `fetch` and `doctor` ask GitHub, one question per owner and two per fork, and a section "Forks" names the commits of the original that the fork lacks and those of the fork that the original lacks, with the command that offers them to it; `status` shows the last comparison with its date. Nothing is synced, opened or pushed.

The new command `tidy` removes the backups and the kept folders older than a month (`--days N`), after the list and one confirmation, and `doctor` lists them. A run cut short now says, at the next run, where the files it had set aside are.

## 1.4.0, 14 November 2026

The command `reset` sets the branch of every repository to the branch it follows on its server, as a fetch and a hard reset would, without the losses of a hard reset. A repository level with its server is left as it is, and one that only lacks the new commits of the server is moved forward. Commits that the server lacks are named, with their number and their first subjects, and dropped only with `--discard-local`, after the plan and one confirmation. Before any branch moves, its commit is kept under a reference of its own, `refs/gh-batch/before-reset/BRANCH/DATE-TIME`, and the report prints the one command that puts the branch and its files back. Uncommitted changes to tracked files, an operation in progress, a detached HEAD and a branch that follows nothing leave a repository alone; untracked and ignored files are never deleted or overwritten, since the move is a checkout that refuses to overwrite them; nothing is pushed, and `--dry-run` only says what would be done. When the history of the server was rewritten and pushed by force, as after `git filter-repo`, the report says so: that is the case the command was made for, where `pull` can only report the old commits as diverged.

The README names five options that the program had and that it never mentioned: `--diverged`, `--no-commit`, `--orgs`, `--no-color` and `--version`. The help of `clone` lists `--orgs` too, and the completion offers it. A citation file lets GitHub show how to cite the program.

## 1.3.0, 14 November 2026

The command `commit` commits the pending changes of every repository. The list is shown first, and the first line of the commits is asked for: Enter takes the sentence "A Regular Commit to Synchronise", another line replaces it, and a minus sign alone does nothing. The same guards as the evening commit apply, a repository that opted out is left alone, and a repository without a remote is committed and stays on this machine. The form `commit push` does this and then the push, which asks on its own; declining the push leaves the commits where they are. With `-m`, with `--yes`, or with `gh-batch.message` set, the message is the one given, and the evening push keeps its own work-in-progress line.

## 1.2.0, 13 November 2026

The command `clone` reads the organisations of the account. Without an owner on its command line it lists the repositories of the account that `gh` is logged in to and of every organisation that this account belongs to. The account goes to the top of the destination, as before, and each organisation into a folder of its own: the one that the new setting `gh-batch.OWNER.folder` names, else the one where clones of the organisation already are, else its name on GitHub.

The first time an organisation has something to clone, its folder is asked for, before the list and the confirmation: Enter takes the folder proposed, another name replaces it, a minus sign leaves the organisation out, and the answer is kept in git's configuration (`gh-batch.OWNER.folder`, `gh-batch.OWNER.skip`), so the question does not return. A run with `--yes`, with `--dry-run` or without a terminal asks nothing and takes the folder proposed. The option `--no-orgs` and the setting `gh-batch.orgs false` keep `clone` to the account alone, and an owner named on the command line is read alone, as before.

An organisation that GitHub refuses to list is named in the report and does not stop the others. No clone is made below a folder that is itself a repository, at any level between the destination and the clone. The leftovers of a run that died are removed from every folder that is about to receive a clone, and `doctor` sees them one level deeper. While GitHub is asked for its lists, a line says which one is being read. An interrupt that comes while a question waits, the one about a folder or the confirmation, ends the run at once with nothing done, instead of waiting for the end of the line, and the time spent waiting for an answer no longer counts in the duration that a run reports.

## 1.1.0, 13 November 2026

The report is easier to read at a glance. Every repository carries a sign: a tick for what was done, a dot for nothing to do, arrows for commits to push or to pull, a cross for what needs you; the names are bold, the branches cyan, the commits in the yellow of git, the changed files named in words with the colour of their change, and the summary coloured the same way. A spinner shows the progress of a run, and a run of some length says how long it took. The colours are the sixteen of the terminal, so that they follow its theme; a pipe, a notification, `--color never` and `NO_COLOR` keep the plain text, and a terminal that is not UTF-8 gets letters in place of the signs.

## 1.0.0, 13 November 2026

First release.

The three commands of the daily routine are there. The command `pull` fetches every repository and moves its branch forward; when both sides have commits it reports, rebases or merges according to `gh-batch.diverged`, and it undoes a conflict so that the repository is left as it was. The command `push` shows what it will do and asks once, commits pending changes behind four guards when `--commit` or `gh-batch.commit` asks for it, pushes each branch to its own destination without ever forcing, and takes the newer commits of the server before a second try. The command `clone` brings what is missing from a GitHub account or from a layout file, each clone under a temporary name until it is complete.

Around them, `sync` chains the pull and the push, `status` shows what is pending without the network, `fetch` says what a pull would do, `log` lists the commits of a period across the repositories, `exec` runs a command in each of them, `doctor` names what is wrong in the repositories, in their remotes and around them, `list` prints the repositories or their layout, `config` prints the settings, and `completion` serves bash and zsh.

The repositories are handled several at a time and reported in the order of the folders. Every long step runs in a process group of its own, so that an interrupt ends the network steps at once and lets a step that moves files finish. The settings live in the configuration of git, the moves of every branch are recorded in a journal, and a report can be handed to a command for the runs that nobody watches.

The installer copies the program or links it from a clone, and the file at the root of the repository also makes it an extension of the GitHub CLI. The tests run without network on Linux, on macOS and under bash 3.2.
